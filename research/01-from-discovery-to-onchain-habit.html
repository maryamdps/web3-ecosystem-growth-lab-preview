01 / THE ECOSYSTEM

A blockchain is infrastructure.
The ecosystem is everything built around it.

A blockchain ecosystem is not just a chain. It is a stack of infrastructure, access tools, applications, developers and communities. Each layer solves a different problem — and each can introduce friction that affects adoption.

01 · Foundation

Network

A distributed ledger maintained by a network of participants. Nodes verify transactions against shared rules, while consensus helps the network agree on the state of that ledger. This is the foundation for ownership and execution without relying on one central operator.

02 · Access

Wallet

A wallet manages the cryptographic keys that let a person control assets and authorise transactions. It is also the user’s gateway: onboarding, recovery, signing, network selection and fee payment all shape the first experience.

03 · Utility

Applications

Applications use smart contracts — programs deployed on a blockchain — to deliver services such as lending, trading, games or digital identity. The application creates the user-facing value; the network provides the underlying execution and settlement environment.

How the pieces connect: a user interacts with an application, usually through a wallet. The wallet requests a transaction signature; the application submits it to the network; the network executes the relevant smart contract and updates its shared state. The result — such as a token transfer or an in-app action — can then be verified on-chain.

02 / SCALING

Layer 1 and Layer 2, in simple terms.

As activity grows, a base chain can become expensive or slower to use. Layer 2 systems aim to increase capacity while keeping a connection to Ethereum. The details matter: “Layer 2” describes a family of designs, not one identical technology.

LAYER 1

Ethereum

Ethereum is a Layer 1: it processes transactions, executes smart contracts and maintains its own consensus. Its decentralised validator network is a key part of its security model. Demand for blockspace can make transactions costly or slow during busy periods.

LAYER 2

Base · Arbitrum · ZKsync

Layer 2s execute transactions outside Ethereum’s main execution layer, then publish data and/or proofs back to Ethereum under their specific design. This can reduce user costs and increase throughput. Base, Arbitrum and ZKsync are prominent examples, but their technical architectures and security assumptions differ.

Think of it this way: Ethereum is the shared railway foundation. Layer 2s are different metro systems connected to it. The analogy helps explain scaling, but it has limits: L2s differ in how they execute transactions, publish data, prove correctness and handle withdrawals. Users should also consider bridges, liquidity fragmentation and the risks of moving assets between networks.
Why this matters for growth: lower fees alone do not create adoption. Users still need to know which network an app uses, how to fund a wallet, whether their assets are on the right chain and how to move them safely. Network complexity can quietly become an onboarding problem.

03 / THE GROWTH CHALLENGE

Attention is not adoption.

A funnel is useful, but Web3 adds unfamiliar decisions: wallet custody, signing transactions, gas fees, network selection and irreversible actions. A user can be interested in a product and still abandon it before reaching value.

01 / DISCOVER

Find it

Discovery through communities, creators, search or ecosystem partners. The message should explain the user problem and outcome — not assume people already understand the protocol.

02 / UNDERSTAND

Trust it

Users need to understand the product, risks, fees and what a wallet connection or transaction will do. Unclear permissions and unfamiliar language weaken trust.

03 / ACTIVATE

Try it

Activation is a completed value event: for example, making a first swap, completing a game action or using a useful on-chain feature — not simply connecting a wallet.

04 / RETURN

Value it

Retention depends on recurring utility, habit and a reliable experience. Incentive-driven transactions may create activity spikes without building lasting usage.

Measure the right behaviour: track the journey from qualified visits to wallet creation, first meaningful transaction, repeat activity and retained users. Separate unique users from transaction counts: automated activity, bots or incentive campaigns can inflate volume without representing durable adoption.
04 / STRATEGIC HYPOTHESES

Three places a growth team can start.

The following are starting points for a growth team. Each should be tested against a specific audience, product and measurable behaviour.

Make discovery useful

Build journeys around intent — “earn”, “trade”, “play” or “create”. Test whether use-case-led landing pages improve qualified product exploration versus infrastructure-led messaging.

Design for first success

Map every step from landing page to first value event. Identify drop-offs around wallet installation, funding, bridging, gas and transaction signing; prioritise the biggest barrier rather than redesigning everything.

Build a reason to return

Identify the natural repeat-use trigger: portfolio activity, a game loop, creator earnings or a recurring service. Compare cohorts with and without incentives to see whether users return after rewards end.

05 / WHAT TO VALIDATE

Turn the framework into evidence.

A useful next research step is to move from general principles to one ecosystem and one user journey.

Research question 01

Where do users hesitate?

Observe first-time users completing a task. Record confusion, failed steps and points where they seek help.

Research question 02

What creates real value?

Compare activation and repeat-use patterns across product features, acquisition sources and user segments.

Research question 03

What brings them back?

Review cohort retention and interview returning and churned users to understand the underlying motivation.
