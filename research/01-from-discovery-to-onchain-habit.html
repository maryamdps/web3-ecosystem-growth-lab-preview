01 / The big picture

A blockchain is not the whole ecosystem.

Think of a blockchain as shared digital infrastructure. The wider ecosystem includes the people, products and services that make that infrastructure useful.

In plain English

What is a blockchain?

A shared digital record that a network of computers helps maintain. Participants follow agreed rules to check and record updates, rather than relying on one company to hold the only copy.

The important distinction

The network is the foundation. The experience is what people come for.

Most people do not wake up wanting to use a blockchain. They want to send value, access an app, trade, play, collect or build something.

Imagine a city

Roads, water and electricity are essential infrastructure. But a city becomes valuable through its homes, shops, schools, services and people.

↔
Now imagine a blockchain ecosystem

The network is infrastructure. Wallets, apps, developers, communities and users create the experiences around it.

Map the ecosystem

Each part has a role. The parts connect — and the experience breaks down when one of them is difficult to use.

02 / Follow the action

What happens when someone makes a transaction?

Let's follow a simple example: a person uses a wallet to send a digital token. This is a simplified explanation; exact steps vary by network and wallet.

From a tap to a network record

The wallet prepares and signs an instruction. The network checks it against its rules, processes it and records the result.

Conceptual flow only. Network consensus, transaction ordering, fees and finality differ across blockchains.
STEP 01

Choose an action

For example, enter a recipient and amount in a wallet.

STEP 02

Review and approve

The wallet asks the user to review details and sign with their key.

STEP 03

Network processing

Network participants check and process the submitted transaction.

STEP 04

Check the outcome

The user can inspect whether it succeeded, failed or is still pending.

Why this matters for growth: every step is part of the user experience. Unclear fees, confusing approvals, network selection or long waits can cause someone to stop before reaching the value of the product.
03 / The building blocks

Seven ideas that make the rest easier to understand.

Keep these definitions nearby. You do not need to master the technical detail to understand the basic user journey.

01 / THE RECORD

Blockchain

A shared record of transactions and data maintained according to network rules.

Think: a shared record book.
02 / ACCESS

Wallet

Software that manages keys used to access assets and approve blockchain actions. It does not literally store coins inside the app.

Think: keys to your digital account.
03 / AN ACTION

Transaction

An instruction submitted to a blockchain, such as sending a token or interacting with an application.

Think: submitting a request.
04 / AUTOMATION

Smart contract

A program deployed on a blockchain that executes according to its code when called.

Think: a rule-based digital machine.
05 / THE PRODUCT

dApp

A decentralised application that uses blockchain networks or smart contracts for some of its functions.

Think: an app with blockchain components.
06 / THE RECORDING

On-chain

An action or data recorded or executed on a blockchain. Not every action inside a crypto product happens on-chain.

Think: visible in the network record.
07 / THE NETWORK LAYERS

Layer 1 / Layer 2

Layer 1 is a base blockchain. Layer 2 systems are built to extend a base network, with their own technical and security trade-offs.

Think: base network + scaling system.

A wallet is more like a keyring

Your assets are represented on the blockchain. The wallet helps manage the keys that let you access them and approve actions.

A smart contract follows rules

It is not a human contract. It is code that carries out actions when the required conditions are met.

04 / Network design

Ethereum is the railway. Layer 2s are different metro systems.

Ethereum Mainnet is the underlying Layer 1. Layer 2 networks process transactions on their own networks, then connect back to Ethereum for important parts of data availability, security and settlement. They exist to help Ethereum support more activity without every user transaction needing to be executed directly on Mainnet.

Layer 1 · Ethereum Mainnet

The city's core railway infrastructure.

Ethereum provides the shared foundation: its consensus rules, validator network and settlement layer. It is highly secure and decentralised, but block space is limited. When demand is high, users compete to have transactions included, which can make fees rise.

Layer 2 · Base, Arbitrum and ZKsync

Separate metro systems connected to the main network.

Each Layer 2 has its own transaction-processing environment, applications and operating design. It can handle many user actions without asking Ethereum Mainnet to execute each one individually, then submits data or proofs to Ethereum according to its design.

One underlying railway. Different metro networks.

The analogy: Ethereum is the shared foundation. Layer 2s run their own services and stations, while connecting back to the underlying system.

A teaching analogy, not a literal network map. Each Layer 2 is a distinct blockchain network with its own design. The lines represent connections to Ethereum, not a claim that every transaction travels directly through Ethereum.
Why not just use Ethereum for everything? Every blockchain has limits on how much activity it can process. When demand for Ethereum block space rises, transactions can become more expensive. Layer 2s move much of the transaction execution away from Mainnet and bundle information or proofs back to Ethereum. This helps increase capacity and reduce costs, while retaining important connections to Ethereum's security and settlement. The exact guarantees depend on the Layer 2's design.
HOW THEY DIFFER

Not all metro systems use the same technology.

A major difference between Ethereum Layer 2s is how they show that transactions were processed correctly. Two common rollup approaches are optimistic rollups and zero-knowledge (ZK) rollups.

01 · Optimistic rollups

Think: accepted unless challenged. Transactions are processed on the Layer 2. The system assumes the submitted result is valid, while a fraud-proof process allows an invalid result to be challenged. The challenge and withdrawal rules depend on the network.

Examples: Base and Arbitrum One.

02 · ZK rollups

Think: prove the result mathematically. Transactions are processed on the Layer 2 and grouped into batches. A cryptographic validity proof is generated and checked by a smart contract on Ethereum.

Example: ZKsync Era.

Important: “Optimistic” does not mean careless, and “zero-knowledge” does not mean the network hides all transaction information. These are names for different proof systems. Both approaches have technical trade-offs, and a network's full security also depends on data availability, upgrade controls, sequencers, bridges and other design choices.
NETWORK EXAMPLES

Base, Arbitrum and ZKsync: same broad goal, different systems.

These are examples of Ethereum Layer 2 rollups, not a ranking. Base and Arbitrum One use optimistic rollup designs; ZKsync Era uses validity proofs.

Built using the OP Stack. It has its own applications, users and developer ecosystem. It may be a practical choice when the app or community you want to use is on Base.

Same category does not mean identical. Base and Arbitrum both use optimistic rollup approaches, but they are separate networks with different applications, liquidity, infrastructure, governance and user experiences. ZKsync Era uses a different proof mechanism. That alone does not make it automatically faster, cheaper or better.
PICKING A NETWORK

So, which Layer 2 should you use?

There is no single best Layer 2 for everyone. Start with what you want to do, then compare the network that supports it.

01 / APP

Does the app support it?

Start with the application you want to use. Not every app, token or service exists on every network.

02 / COST

What will the action cost?

Compare the current transaction fee and any deposit, withdrawal or bridge costs. Fees change with demand.

03 / ASSETS

Are your assets and liquidity there?

Check that the token, trading pair, lending market or other service you need is available on that network.

04 / TRUST

Understand the trade-offs.

Check the network's security model, data availability, upgrade controls, bridge route and withdrawal process.

Example: you want to use a DeFi app

If the protocol and the liquidity you need are on Arbitrum One, Arbitrum may be the sensible choice. The fact that another network has a lower advertised fee won't help if the app or market you need isn't there.

Example: you want to try a consumer app

If the app is built on Base and supports your wallet and assets there, Base may be the simplest route. Choose the network that makes the task possible and practical, not the one with the most impressive slogan.

One more distinction: a Layer 2 is not a bridge. Base is a Layer 2 network. A bridge is a separate mechanism for moving assets or messages between networks, such as Ethereum and Base. Bridges have their own risks and fees; they are not the Layer 2 itself.

06 / The growth challenge

Getting attention is not the same as creating adoption.

A person can see a campaign, open a wallet and still never use an application. Sustainable growth means helping people understand the product, experience value and find a reason to return.

The journey from discovery to habit

A practical framework for examining where people progress — and where they get stuck.

01 / DISCOVER

“What is this?”

Someone hears about a network or finds an app that appears relevant.

Possible friction: unclear audience or value proposition.
02 / UNDERSTAND

“Is this for me?”

They understand what it does, how to start, what it costs and what risks exist.

Possible friction: jargon, uncertainty or low trust.
03 / ACTIVATE

“I did it.”

They complete a meaningful first action and experience the product's value.

Possible friction: wallet setup, fees or confusing steps.
04 / RETURN

“I'll use this again.”

They find ongoing utility, community or a reason to return.

Possible friction: no repeat use case or weak product value.

Where should a growth team look?

Measure the movement between stages, then investigate the reasons behind drop-off. Do not assume every user needs the same journey.

An analytical framework, not a measured funnel or benchmark from any one blockchain.
DiscoveryQualified visits, relevant audience reach, app-page visits.
UnderstandingGuide completion, support questions, onboarding comprehension.
ActivationFirst successful action, onboarding completion, time to first value.
RetentionRepeat meaningful actions, returning users, cohort retention.
CommunityHelpful participation, contributor activity, support resolution.
QualityTask success, user feedback, safety incidents and failed actions.
A note on metrics: wallet creation or transaction volume alone does not prove healthy adoption. Incentives, bots, duplicate wallets and one-off campaigns can distort activity. Define meaningful use carefully and establish a baseline before setting targets.

Three experiments I would test next.

These are strategic hypotheses derived from the research — not campaigns that have already been launched or results that have already been achieved.

Discovery

Organise discovery around user needs

Test: Do more relevant visitors reach an app or useful next step?
B
Activation

Build a first-success walkthrough

Show wallet setup, network choice, fees and approvals in plain language. Help a newcomer complete one appropriate, low-risk task.

Test: Do more users complete the first meaningful action?
C
Retention

Create a reason to return

Connect users with recurring utility, useful product updates or ongoing community learning — beyond a short-term reward.

Test: Does meaningful repeat activity improve over time?
How I would approach measurement

Start with a baseline. Then test one friction point at a time.

Set a clear audience, define the desired action, observe where users struggle, run a small experiment and compare outcomes. Targets should come from evidence, not invented benchmarks.
